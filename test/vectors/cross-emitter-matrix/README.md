# Cross-Emitter Signature-Verification Matrix (P3, first slice)

## What this measures

For each pair of MCP SDKs (S_A, S_B) in {TypeScript, Python, Go, Swift, Java, Kotlin, C#, PHP, Ruby, Rust}:

- **Sign:** S_A canonicalizes a record and signs the canonical form with a shared Ed25519 key.
- **Verify:** S_B receives (record, signature), locally recomputes the canonical form from the record, and verifies the signature against the local canonical form.
- **Cell result:** 1 if verification succeeds (S_A and S_B agree on canonical form for this record); 0 if it fails (they disagree, verifier reports tamper without any actual tamper).

This produces a 10×10 grid answering the question **"Does the 26-divergence dataset actually break signature verification, in practice?"**

## First slice (this commit)

TypeScript ↔ Python is implemented as a proof of concept. Both use the same tuple-array canonical form (`verify.mjs` and `verify.py` in the parent directory), so the expected result is:

- TS→TS: 100% verification success
- Python→Python: 100% verification success
- TS→Python and Python→TS: 100% verification success on canonicalization-safe inputs, 0% on inputs that trigger a canonicalization divergence between the two.

## Extension path (weeks 3-6, one SDK at a time)

Each additional SDK requires:
1. A canonical-form signer script that follows the tuple-array construction in `verify.mjs`.
2. A canonical-form verifier script that recomputes canonical form and verifies an incoming signature.
3. Registration in `run-matrix.sh` under the SDK's language key.

The remaining eight SDKs (Go, Swift, Java, Kotlin, C#, PHP, Ruby, Rust) each take 3-5 hours to implement based on existing `serialize-sdk-*` scripts in `../runners/`.

## Files

- `sign.mjs` — TypeScript/Node.js signer: reads a record from stdin, prints canonical form + signature (hex) as JSON.
- `verify.mjs` — TypeScript/Node.js verifier: reads (record, signature) pair from stdin, verifies against locally-recomputed canonical form.
- `sign.py` — Python signer: same protocol.
- `verify.py` — Python verifier: same protocol.
- `run-matrix.sh` — orchestration: runs each (signer, verifier) pair against a shared vector set and produces a JSON matrix.
- `matrix-results.json` — output of the matrix run (written on each execution).

## Running

```bash
cd test/vectors/cross-emitter-matrix
./run-matrix.sh
cat matrix-results.json | jq
```

## Reproducibility

The Ed25519 key material is generated fresh per run and shared across signers via `SHARED_KEY.hex` (32 bytes hex). The vector set comes from `../canonicalization.json` (existing 19-vector suite plus the 40-test cross-SDK harness).

**Reading the result:**

- **45 of 45 "correct" cells pass.** TypeScript, Python, and Go implementations of the tuple-array canonical form produce byte-identical output. Signatures generated by any one of the three verify under the other two. Same result for records containing Unicode edge cases (`café`, `😀-agent`, tab/newline sequences).

- **15 of 15 "buggy" cells fail.** The buggy verifier deliberately misimplements canonicalization: it uses raw `JSON.stringify(record)` instead of the tuple-array construction. Every signature from every correct signer fails verification under the buggy variant. This demonstrates that the matrix surfaces canonical-form divergences correctly.

**Why the buggy row matters:** it simulates what happens when a real SDK skips the tuple-array canonical form (a plausible bug: any implementation could accidentally call `JSON.stringify` on the record object rather than following the field-order + type-tagged construction). The matrix cell shows verification silently fails — no tampering, no wire corruption, just canonical-form divergence causing false-positive verification failures.

**What the 10-SDK extension will surface:** SDKs that cannot easily produce the tuple-array canonical form (Swift's Foundation JSONEncoder sorts differently; PHP escapes forward slashes; C# HTML-escapes; TypeScript's silent 2^53+1 precision loss) will fail verification cells for inputs that trigger their specific divergence, exactly as the buggy row demonstrates. Those cells are the paper's headline finding: "SDKs that do not adopt the canonical form cannot participate in cross-emitter audit-chain verification."
